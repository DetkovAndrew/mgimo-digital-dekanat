# Домен и HTTPS: подготовка для VPS

**Передача сокоманднику:** 11.11 пользователь поручил сервер и развёртывание
второму участнику. Здесь только подготовленные шаблоны и порядок действий;
создание Yandex Cloud и дальнейшая настройка сервера в этой сессии прекращены.
Зарегистрированный адрес: `university-dekanat.duckdns.org`; текущая запись — `0.0.0.0`.
После выбора VPS указать его IP и выполнить проверки ниже. Токен DuckDNS
получить у владельца аккаунта через безопасный канал, не через репозиторий.

Состояние 11.11.2026: `university-dekanat.duckdns.org` зарегистрирован,
DNS пока `0.0.0.0`. Пользователь подтвердил, что сервера ещё нет.
Конфигурации подготовлены локально, **не применены и не проверены через `nginx -t`**:
доступного VPS нет, локальный Docker daemon не запущен. Сайт ещё не опубликован.

## Какой сервер нужен

Ориентир: Ubuntu LTS, 2 vCPU, 4 ГБ RAM, SSD 30–50 ГБ и постоянный публичный IPv4.
Это начальная конфигурация для демо, не результат нагрузочного теста.
Проверить стоимость диска и IPv4 отдельно. Подтверждение банковской карты,
условия платёжного аккаунта и платёж выполняет владелец аккаунта.
Самостоятельная покупка серверов в этом проходе не выполнялась.

Для нового подходящего аккаунта рассматриваем стартовый грант Yandex Cloud;
если условия не подходят — сравнение платных VPS в `docs/research/hosting.md`.
Не считать бесплатный DNS бесплатным сервером.

### Yandex Cloud: текущее состояние

Пользователь подтвердил, что ранее Yandex Cloud не использовал. Это подходит под
часть условий стартового гранта; окончательное право и начисление подтверждаются
только в биллинге. 11.11 консоль `https://console.yandex.cloud/` во встроенном
браузере не загрузилась (таймаут); аккаунт, биллинг и VM этим проходом не создавались.

Владелец открывает консоль в обычном браузере, входит с Яндекс ID и создаёт первый
личный платёжный аккаунт. Для стартового гранта карту нужно привязать **при создании**
этого аккаунта, не позже. Для резидентов РФ документация указывает грант от 4 000 ₽
на 60 дней при выполнении остальных условий. После активации проверить фактическое
начисление и остаток; не считать облако безусловно бесплатным после исчерпания гранта.
До создания ресурсов нужно сверить финальную смету с остатком гранта.
Ввод карты, SMS/3-D Secure и принятие условий выполняет сам владелец.

## Схема

DuckDNS A-запись → публичный IPv4 VPS → Nginx 80/443 → Next.js на 127.0.0.1:3000.
PostgreSQL доступен приложению, его порт наружу не публикуется.

Эти конфигурации рассчитаны на Nginx, установленный **на самом VPS**.
Если Nginx будет в контейнере, адрес `127.0.0.1:3000` нужно заменить адресом
приложения в сети контейнеров; не применять шаблон без проверки топологии.
Полный деплой приложения/БД и управление процессами здесь пока не реализованы.

## После получения VPS

1. Получить IP, SSH-логин и способ входа без передачи приватного ключа в чат/Git.
   До записи конфигураций проверить, какие сервисы уже работают на сервере.
2. Поднять production-приложение и постоянную PostgreSQL, настроить перезапуск
   процессов. Использовать миграции существующей истории. Seed создаёт данные
   только для нового демо-стенда; не сбрасывать БД с нужными данными.
3. Задать серверный `BETTER_AUTH_URL=https://university-dekanat.duckdns.org`,
   отдельный случайный `BETTER_AUTH_SECRET` и остальные секреты в окружении сервера.
   Локальный `.env` разработки не заменять production-файлом.
4. В DuckDNS указать публичный IPv4 этого VPS. Поле IPv6 оставить пустым, если
   IPv6 на сервере не настроен. Проверить A/AAAA с нескольких DNS-резолверов.
5. Разрешить входящие 80/443, SSH ограничить доступом администратора.
   Установить Nginx и Certbot из пакетов ОС. Сохранить существующую конфигурацию
   перед изменениями, не затирать другие сайты на сервере.
6. Создать `/var/www/letsencrypt/.well-known/acme-challenge/` и подключить
   **только** `nginx/university-dekanat.bootstrap.conf`. Проверить `sudo nginx -t`,
   затем перечитать конфигурацию. Веб-корень для ACME должен читаться Nginx.
7. Создать проверочный файл в ACME-каталоге и убедиться снаружи, что он доступен
   по HTTP. При ошибках DNS/порта 80 сертификат пока не запрашивать.
8. Выпустить сертификат штатным Certbot; имя сертификата закреплено явно:

```bash
sudo certbot certonly --webroot --webroot-path /var/www/letsencrypt \
  --cert-name university-dekanat.duckdns.org \
  -d university-dekanat.duckdns.org
```

Certbot попросит контактный email и принятие условий; не подставлять выдуманные
данные и не записывать ключи в репозиторий.

9. Только после появления сертификата заменить bootstrap-блок итоговой
   `nginx/university-dekanat.https.conf`, проверить `sudo nginx -t` и перечитать Nginx.
   **Оба файла одновременно не включать:** в них один и тот же HTTP server_name.
10. Проверить системный таймер автоматического продления Certbot и выполнить
    `sudo certbot renew --dry-run`. Добавить deploy-hook, который выполняет
    `nginx -t` и reload после успешного продления; иначе Nginx останется со старым
    сертификатом в памяти. Конкретные пути команд проверить на выбранной ОС.

## Что считается готовым

- HTTP переводит на HTTPS; сертификат соответствует полному имени.
- Вход обоих студентов и серверные действия работают с публичным HTTPS-origin.
- Чужая заявка/дисциплина/пара возвращает 404; личные ответы не кешируются публично.
- После перезапуска приложения и БД заявки сохраняются.
- Проверены домашний и мобильный интернет в РФ без VPN.
- Оплата/грант/ресурсы покрывают период до конца 28.11.2026 МСК.

Пока ни один пункт проверки внешнего VPS не выполнен.
