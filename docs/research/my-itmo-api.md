# Исследование: my.itmo глазами API (репозиторий my-itmo-api)

Источник: https://github.com/alllexey-dev/my-itmo-api (MIT, неофициальная Kotlin-библиотека,
коммит `9cad9a0`, 2026-11-09). Изучены README и `kmp/fixtures/*` — по словам автора, фикстуры
синтетические, реальных данных в них нет. Код не запускали и не подключали.

**Мы не интегрируемся с my.itmo**: ТЗ запрещает подключать прототип к реальным системам вуза
и использовать настоящие логины. Репозиторий — только справка о реальной структуре данных,
чтобы наши вымышленные данные и сценарии выглядели правдоподобно.

## Разделы my.itmo (по API)

`schedule`, `recordBook` (зачётка), `personalities` (поиск людей), `studyplan`, `qr` (пропуск),
`sport`, `election` (выбор дисциплин), `finances`, `dormitory`, `requests`, `system` (меню, дашборд), `bars` (БаРС-журнал).

## Что берём в модель University

| Наблюдение | Как используем |
|---|---|
| Пары начинаются в 08:20 и длятся 1 ч 30 мин, есть таблица `time_slots` | Сетка пар University: 08:20, 10:00, 11:40, 13:30, 15:20, 17:00, 18:40 (демо) |
| У пары: `building` (полный адрес), `room`, `format` (очно/дистанционно), `zoom_url`, `work_type` | Корпус как отдельная сущность с координатами; формат и ссылка на онлайн-занятие |
| Зачётка: `current_score` (например, 71.5), `rate` вида «4/C», `attempt`, `control_type`, `exam_date` | Баллы + оценка/буква ECTS, попытки, дата аттестации |
| БаРС: контрольные точки с `mark` и максимумом, «Удвл., E» | Контрольные точки с maxPoints, итог по шкале БаРС |
| Заявки: `name`, `notice`, `status_name`, `created_at/updated_at` — плоский список без истории | **Наш плюс**: история статусов, комментарии деканата, ответ на уточнение |

## Спорт — главная точка улучшения

Как устроено (по API):
- запись на **отдельное занятие**; результат `Booked` / `Full` («мест нет, попробуйте позже»);
- ограниченное число **попыток записи** (`total/used/free_attempts`), окно записи `sign_duration: 7` дней;
- недельные **лимиты** по типам (`limit`/`available`), у занятия `limit`/`available` мест;
- флаг `intersection` и `can_sign_in` с `unavailable_reasons` — пересечения уже проверяются;
- `debt.needed_score` — сколько баллов не хватает до зачёта; баллы за посещения и соревнования;
- экстернат и проекты как альтернативные форматы зачёта.

Вывод: проблема не в отсутствии проверок, а в **механике «кто первый»**: места кончаются → `Full`
→ студент обновляет страницу. University заменяет это жеребьёвкой по приоритетам
(см. `docs/ai-log/codex/05-concept-itmo.md`), показывает причину недоступности человеческим языком
и связывает запись с расписанием, маршрутом и прогрессом «нужно ещё N баллов».
