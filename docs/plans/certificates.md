# Электронная справка с QR-проверкой

Запрос капитана (14.11): «справка с QR». Сейчас заявка доходит до «Готово», а документ «в демо не выдаётся»:
сценарий обрывается на самом интересном месте. Цель: деканат выпускает справку, студент скачивает PDF, работодатель
сканирует QR и видит, что справка настоящая. Первая версия — только «Справка об обучении» (`study_certificate`).

## Сценарий

1. Студент подаёт «Справку об обучении», формат «Электронная: PDF с QR-кодом проверки».
2. Сотрудник деканата переводит заявку «В работе» → «Готово». В той же транзакции (под уже существующей
   блокировкой `FOR UPDATE OF r`) выпускается документ: номер, токен проверки, снимок данных на дату выдачи.
   Бумажный формат и другие типы — как раньше, без документа.
3. Студент в заявке видит карточку «Справка готова»: «Скачать PDF», «Скопировать ссылку для проверки».
   Уведомление о готовности говорит, что PDF в заявке.
4. На PDF — QR со ссылкой `https://<домен>/verify/<токен>`. Открытая страница без входа отвечает
   «Справка найдена в демо-реестре» и показывает минимум данных для сверки. QR подтверждает существование записи,
   а не неизменность предъявленного PDF: страница просит сверить данные с документом (ревью Codex 57).

## Данные

Новая таблица `issued_document` (миграция + CHECK вручную):

| Поле | Что |
|---|---|
| `id` | cuid |
| `number` | autoincrement, уникальный; показ «С-000012» |
| `requestId` | уникальный FK на `request` (`onDelete: Cascade`): одна справка на заявку |
| `kind` | `study_certificate` (CHECK по списку) |
| `verifyToken` | 16 случайных байт `randomBytes` → base64url, 22 символа, уникальный; CHECK `^[A-Za-z0-9_-]{22}$` |
| `content` | JSON-снимок на дату выдачи (zod-схема в коде): ФИО, факультет, направление, профиль, уровень, курс, группа, форма обучения, основа, дата зачисления, «куда предоставить», число экземпляров |
| `issuedAt` | timestamptz |

Владельца отдельно не храним: он определяется через заявку (`where: { requestId, request: { studentId } }`),
поэтому рассогласование «документ одного — заявка другого» невозможно. Снимок не меняется при правке профиля:
PDF через месяц такой же, как в день выдачи.

Токен — секрет доступа к сведениям о студенте (пусть и сокращённым). 128 случайных бит достаточно против угадывания;
открытое хранение в БД — осознанный компромисс прототипа: PDF перерисовывается при каждом скачивании и должен
содержать тот же адрес. Токен не попадает в снимок помощника, уведомления, список заявок и журналы.
После выпуска владелец и тип заявки неизменны — триггер `request_fixed_after_document` (ревью Codex 57).

## Доступ

- `GET /api/requests/[id]/document` — PDF только владельцу заявки: `studentForApi()` (401 без сессии),
  `issuedDocument.findFirst({ where: { requestId: id, request: { studentId } } })`, чужое или нет документа — 404.
  Заголовки: `application/pdf`, `Content-Disposition: attachment` (ASCII-имя + `filename*`),
  `Cache-Control: private, no-store`, `nosniff`. GET без побочных эффектов: статус заявки не меняется.
- `/verify/[token]` — открытая страница вне кабинета, с дисклеймером. Неверный формат или неизвестный токен —
  одинаковая страница «Справка не найдена» (настоящий HTTP 404), без различия причин. Показывает: «Справка найдена»,
  вид, номер, дату выдачи, **фамилию и инициалы** («Морозова А. В.», сокращает сервер), факультет, курс, форму
  обучения — ровно то, что работодатель сверяет с бумагой. DAL возвращает отдельный объект только с этими полями,
  собранный из снимка. Не показывает: группу, номер зачётки, основу обучения, дату зачисления, «куда предоставить»,
  id заявки и студента, текущее состояние студента.
- Заголовки: `Referrer-Policy: no-referrer` (приложение для `/verify/*` и `<meta name="referrer">`; в Caddy политика
  стала значением по умолчанию `?Referrer-Policy`), `noindex` (метаданные и Caddy), динамическая страница без кеша.
  Внешних ресурсов и аналитики нет.
- Перебор токенов бессмыслен (2^128), но лимит 30 проверок в минуту с адреса бережёт БД (в памяти, как у помощника).
- Сотрудник документ не скачивает (в первой версии не нужно); в карточке заявки видит «Выпущена справка С-000012».
- Исключение в AGENTS.md: страница проверки — единственная открытая страница с данными студента; только по токену
  из документа, только поля из списка выше.

## PDF

- `pdf-lib` (MIT) + `@pdf-lib/fontkit` (MIT): чистый JS, работает в Node без нативных модулей. QR рисуем
  квадратами из матрицы `uqr` (уже в зависимостях). Шрифт Onest 400/600 TTF (OFL) — в `assets/fonts/onest/`
  с `OFL.txt`; в standalone-сборку — через `outputFileTracingIncludes`, как сертификат GigaChat.
- A4: знак и «University», «Справка № С-000012 от 14.11.2026», таблица полей без склонений
  («Студент: Морозова Алина Витальевна» — пол и падежи не нужны), «Справка выдана для предоставления: …»,
  «Документ сформирован в электронном виде. Подлинность проверяется по QR-коду» вместо подписи, QR с короткой
  подписью адреса. Крупный диагональный водяной знак «ОБРАЗЕЦ · ДЕМО», в подвале дисклеймер конкурса.
- Даты в PDF — `CreationDate` и `ModificationDate` = `issuedAt`. Обещаем неизменность **данных** (снимок с версией
  `v: 1`), а не байтов файла: шаблон может улучшаться.
- Адрес в QR — из `BETTER_AUTH_URL` (на сервере `https://university-dekanat.duckdns.org`).

## Интерфейс

- Каталог: у `study_certificate` формат «Электронная: PDF с QR-кодом проверки»; у остальных справок пометка
  «в демо не выдаётся» остаётся.
- Заявка студента: карточка «Справка готова» над «Данными заявки» — главная кнопка «Скачать PDF», вторичная
  «Скопировать ссылку для проверки» и строка «Работодатель может проверить справку по QR-коду».
- Страница проверки: одна главная карточка (галочка + «Справка подлинная»), таблица полей, пояснение, что это
  демо-сервис конкурса; 360 px, обе темы.

## Тесты

- Модульные: формат номера, сокращение ФИО, какие заявки выпускают PDF, формат токена.
- Интеграционные (`tests/integration/documents.test.ts`): «Готово» по электронной справке — один документ со
  снимком и номер в уведомлении (без токена); бумажная и другие виды — ни одного; «Выдана» не меняет документ;
  неполный профиль — отказ без записей; сотрудник другого факультета — 404; два одновременных «Готово» — одна
  справка; отзыв студентом против «Готово» — справка только у победившего «Готово»; триггер владельца и типа;
  скачивание A — PDF (заголовки, одна страница, заголовок документа), B — 404, без сессии — 401, сотрудник — 403;
  токен только в своей заявке; проверка — ровно разрешённые поля, изменения профиля после выдачи не видны;
  изменённый, чужой формат и пустой токен — null; лимит проверок; PDF с длинными строками, управляющими символами
  и эмодзи — одна страница.
- Вручную: PDF растрирован (PyMuPDF) и QR распознан jsQR при 72, 110 и 150 dpi; полный путь в браузере на 360 px
  в обеих темах; HTML страницы проверки не содержит ФИО целиком, группы, зачётки, основы и id.

## Не входит

Отзыв справки, другие виды документов (выписка оценок), скачивание сотрудником, подпись ЭЦП. Отзыв заявки после
«Готово» по-прежнему невозможен (переходы сотрудника: из «Готово» только «Выдана»). Старые выполненные заявки без
документа показывают «PDF для этой заявки не выпускался»; скачивание ничего не создаёт.
