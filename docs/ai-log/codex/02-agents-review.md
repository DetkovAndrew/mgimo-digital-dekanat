**2. PostgreSQL без Docker и sudo**

**Основной вариант — `embedded-postgres`: настоящий PostgreSQL, запускаемый обычным пользователем.** В среде подтвердились Linux x64 и непривилегированный пользователь — это подходящие исходные условия.

| Вариант | Оценка |
|---|---|
| **`embedded-postgres`** | Максимальная близость к продакшену: обычный PostgreSQL, штатный протокол, Prisma и миграции. Пакет поставляет бинарники; нужны postinstall-скрипты и symlinks. Закрепить версию и major PostgreSQL. [README](https://github.com/leinelissen/embedded-postgres) |
| **PGlite через Prisma 7 `prisma dev`** | Удобный запасной путь: без системной установки, схема PostgreSQL и Prisma Migrate сохраняются. Команда документирована именно для Prisma 7; в Prisma 8 её назначение изменилось. [Документация](https://docs.prisma.io/docs/local-development/postgres) |
| **PGlite напрямую** | WASM PostgreSQL; для подключения обычных PostgreSQL-клиентов есть socket-обёртка. Многосоединённость реализуется через мультиплексирование единственного соединения — блокировки и конкурентные транзакции проверять на настоящем PostgreSQL. [Ограничения](https://pglite.dev/docs/pglite-socket) |
| **Удалённый PostgreSQL на имеющемся сервере** | Резерв при проблемах с бинарниками. Отдельные БД каждому разработчику и тестовому запуску, защищённое подключение; зависимость от сети. |
| **SQLite / `pg-mem`** | Не использовать как основную интеграционную БД: не обеспечивают требуемую одинаковость PostgreSQL-схемы и поведения. |

Предлагаемый порядок для Claude:

1. Добавить `embedded-postgres` как devDependency с закреплённой версией.
2. Сделать launcher: инициализация кластера один раз, постоянный каталог данных вне Git, запуск только на `127.0.0.1`, корректная остановка. Проверить права и symlinks на DrvFS; проект не переносить.
3. Создать отдельные `dev`, `shadow` и тестовые БД. **Shadow никогда не направлять на dev/test с нужными данными.**
4. Оставить единый `provider = postgresql`, одну Prisma-схему и историю миграций. Различаются URL и окружение.
5. Разработка — `migrate dev`; чистые интеграционные тесты и продакшен — `migrate deploy`. Тесты получают отдельную БД, затем seed двух студентов. [Миграции](https://www.prisma.io/docs/orm/v7/prisma-migrate/workflows/development-and-production)

**Версии нужно закрепить сейчас:** документация Better Auth пока исключает Prisma 8 — рекомендую совместимую связку Prisma 7, Client и PostgreSQL-адаптера. [Источник](https://better-auth.com/docs/adapters/prisma). Node 26 отсутствует в опубликованной матрице Prisma 7; безопаснее Node 24 рядом в пользовательском каталоге без sudo. Это не доказательство несовместимости Node 26. [Матрица](https://docs.prisma.io/docs/orm/v7/reference/system-requirements)

**3. Набросок моделей Prisma**

`🔒` — обязательная проверка владельца; `👥` — доступ через принадлежность группе.

| Модель | Ключевые поля и ограничения |
|---|---|
| **User** | Стандартные поля Better Auth: `id`, `name`, уникальный `email`, `emailVerified`, даты. ФИО хранить здесь, не дублировать в профиле. |
| **Session, Account, Verification** | Схема установленной версии Better Auth: связи с пользователем, токен/срок сессии, provider/account ID, хеш пароля в Account. Не выдавать через прикладные API. Генерировать штатным инструментом. [Схема](https://better-auth.com/docs/concepts/database) |
| **StudentProfile 🔒** | `id`, уникальный `userId`, `groupId`, `course`. |
| **StudyGroup 👥** | `id`, `code`, `faculty`, `program`. Основную группу получать через профиль текущего студента. |
| **AcademicTerm** | `id`, учебный год, номер семестра, начало/конец. |
| **Discipline** | `id`, название. |
| **CourseOffering 👥** | `id`, `disciplineId`, `groupId`, `termId`, вымышленное отображаемое имя преподавателя. Конкретная дисциплина конкретной группы в семестре. |
| **LessonOccurrence 👥** | `id`, `offeringId`, фактические начало/конец, аудитория, статус занятия. Для прототипа — конкретные датированные занятия без движка повторений. |
| **LessonChange 👥** | `lessonId`, прежние/новые время и аудитория, причина, дата изменения. Перенос сохраняет ID занятия и историю. |
| **Assessment 👥** | `id`, `offeringId`, вид — экзамен/зачёт/работа, название, дата, аудитория или дедлайн. Формирует раздел сессии. |
| **GradeResult 🔒** | `studentId`, `assessmentId`, попытка, оценка либо результат зачёта, дата. Уникальность «студент + испытание + попытка»; согласованность вида и результата. |
| **Request 🔒** | `id`, `studentId`, тип, текущий статус, валидированные поля заявления, даты подачи/изменения. |
| **RequestStatusHistory 🔒** | `requestId`, предыдущий/новый статус, время, инициатор USER/SYSTEM, необязательный `actorUserId`, комментарий для студента. Доступ только через принадлежащую ему заявку. |
| **Notification + NotificationRecipient 🔒** | Содержание, тип, дата публикации, связь с занятием/заявкой; получатель — `notificationId`, `userId`, `readAt`. Уникальность пары; чтение и отметка прочитанного ограничены получателем. |

Общие правила: индексы по владельцам, группе и времени; моменты времени — UTC/`timestamptz`, отображение — `Europe/Moscow`. Изменение статуса заявки, запись истории и уведомление — одна транзакция. Студент самостоятельно не изменяет оценки, расписание и служебные статусы.

**Сотрудник деканата для ТЗ не обязателен.** На первом этапе достаточно реально сохраняемой заявки со статусом «Принята» и демонстрационных заявок с историей. Кабинет сотрудника добавлять после ядра; тогда нужны отдельная роль, ограниченная область доступа и третий тестовый аккаунт.
