**1. Модель данных**

В [schema.prisma](/mnt/c/MGIMO/prisma/schema.prisma) предлагаю:

| Было | Стало |
|---|---|
| `LessonChange` хранит только прежние значения | Добавить новые время/аудиторию и прежний/новый статус. Иначе после нескольких переносов запись не содержит законченного перехода; отмену тоже нельзя полноценно восстановить. |
| Обновление занятия и добавление истории ничем не связаны | В сервисе выполнять **занятие + историю + уведомление с получателями одной транзакцией**. Не создавать новое занятие взамен перенесённого. |
| И `Lesson.teacherId`, и `CourseOffering.leadTeacherId` необязательны | Проще сделать преподавателя курса обязательным; преподаватель занятия остаётся переопределением. Иначе возможна пара без преподавателя, вопреки ядру ТЗ. |
| `GradeResult.grade` и `passed` допускают любые сочетания | Ограничить оценку диапазоном 2–5, попытку — положительным числом; результат содержит либо оценку, либо зачёт. Отсутствие результата — отсутствие строки. Соответствие виду контроля проверять в сервисе. |
| Результат может связать студента с испытанием чужой группы | При записи проверять `student.groupId == assessment.offering.groupId`. Одних внешних ключей недостаточно. |
| `Request.number` — обязательная строка без механизма выдачи | Самый простой вариант: `Int @unique @default(autoincrement())`; вид `З-2026-000123` формировать при отображении. Не использовать `count()+1` или `max()+1`. |
| История заявки независима от текущего статуса | Создавать заявку сразу с первым событием `null → SUBMITTED`. Дальнейшие переходы — по разрешённым правилам, с условным обновлением по прежнему статусу, историей и уведомлением в транзакции. |
| Получателей уведомления можно связать с любой заявкой | Для `REQUEST_STATUS` получателя определять через владельца заявки. Чтение уведомления — только через `NotificationRecipient` текущего пользователя. |

Минимальные ограничения времени: `Lesson.endsAt > startsAt`, корректный порядок дат семестра и сессии. Проверять в сервисах и seed; простые инварианты закрепить SQL `CHECK` в миграции.

По индексам:

- Добавить `[assessmentId]` у `GradeResult`, `[lessonId]` и `[requestId]` у `Notification` для связей и каскадов.

**2. Авторизация и Prisma**

В [auth.ts](/mnt/c/MGIMO/src/server/auth.ts) связка Prisma adapter, username и последний `nextCookies()` выглядит корректно. Порядок плагинов соответствует [интеграции Better Auth с Next.js](https://better-auth.com/docs/integrations/next).

- **`input:false` защищает `role` в штатных запросах Better Auth.** Проверил установленный код: при создании используется default, при обновлении запрещённое значение отвергается. Комментарий «ни при каких запросах» → «в штатных входных данных Better Auth; собственные обработчики отдельно ограничивают поля». Это не защищает от небезопасного `prisma.user.update({...body})`. [Описание поля](https://better-auth.com/docs/concepts/database).
- **`trustedOrigins` для одного origin необязателен**, если задан корректный `BETTER_AUTH_URL`: его origin доверенный автоматически. Дополнительные точные origins нужны, например, для второго адреса разработки. Wildcard не нужен. В продакшене обязательно задать канонический HTTPS URL и секрет. [Настройки](https://better-auth.com/docs/reference/options).
- **Rate limit настроен, но действует на HTTP-запросы.** Вход через Server Action с прямым `auth.api.signInUsername()` обходит этот limiter. Предпочтителен штатный HTTP endpoint; иначе нужен отдельный лимит. За Nginx доверять только заголовку IP, который прокси перезаписывает, и закрыть прямой доступ к Next. [Ограничения limiter](https://better-auth.com/docs/concepts/rate-limit).

**Seed:** текущий `auth.api.signUpEmail()` с `disableSignUp:true` завершится ошибкой — запрет действует и при серверном вызове.

Предпочтительный путь: отдельный экземпляр конфигурации **только внутри CLI seed**, с регистрацией и `autoSignIn:false`, без `nextCookies`; создание через `auth.api`. Основной HTTP auth остаётся закрытым. Роль сотрудника назначать отдельной доверенной записью вместе с профилем: `input:false` не даст передать её через регистрацию.

Прямой хеш тоже допустим: `hashPassword` из `better-auth/crypto`, затем транзакционная запись User/Account/профиля. При этом нужны `providerId:"credential"`, `accountId:user.id`, нормализация username/email и идемпотентность. Самостоятельный формат хеша не вводить.

В [db.ts](/mnt/c/MGIMO/src/server/db.ts) singleton и `PrismaPg` корректны. Дополнительно:

- Generated client игнорируется Git, но генерации в scripts пока нет → добавить обязательный `prisma generate` перед сборкой.
- `server-only` ставить в веб-слое доступа. Не добавлять вслепую в конфигурацию, которую импортируют seed и Better Auth CLI.

`prisma7.config.ts` действительно распознаётся установленной 7.10.1. `process.loadEnvFile` и отдельная shadow-БД здесь нормальны. Каталог PostgreSQL вне DrvFS оставляем.

**3. Общий слой доступа**

Предлагаю такие сигнатуры:

```ts
requireStudent(): Promise<Readonly<{
  userId: string; studentId: string; groupId: string;
}>>

requireStaff(): Promise<Readonly<{
  userId: string; staffId: string; faculty: string;
}>>

getMyRequest(id: string): Promise<RequestDTO>
createMyRequest(input: CreateRequestInput): Promise<RequestDTO>
listMyGrades(termId: string): Promise<GradeDTO[]>
markMyNotificationRead(notificationId: string): Promise<void>
```

Каждая публичная функция DAL **сама вызывает guard**. Она не принимает владельца или контекст авторизации от вызывающего кода.

Guard получает сессию через `auth.api.getSession({ headers: await headers() })`, проверяет точную роль и загружает соответствующий профиль по `session.user.id`. **`studentId` в стандартной сессии сейчас нет** — его нужно получить из БД. Неизвестная роль или отсутствующий профиль означают отказ.

Паттерны запросов:

- Заявка: `where: { id, studentId }`.
- История: `where: { requestId, request: { studentId } }`.
- Расписание: фильтр через `offering.groupId`.
- Уведомление: через получателя с `userId` из guard.
- Сотрудник: фильтр через `student.group.faculty`; одного `requireStaff()` недостаточно.

Прямые импорты Prisma из страниц и Actions запретить линтером: только DAL, конфигурация авторизации и CLI-скрипты. DAL возвращает ограниченные DTO; чужой объект превращает в 404. Проверку владельца сохранять непосредственно в запросе изменения, а не только в предварительном чтении.
