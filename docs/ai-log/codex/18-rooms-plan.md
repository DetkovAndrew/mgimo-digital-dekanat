# Codex 18: Ревью плана схемы корпуса и брони аудиторий

## Запрос

> docs/plans/rooms.md: интерактивная SVG-схема корпуса, бронирование аудиторий студентами, связка с помощником (шаблонные ссылки, предзаполнение заявки). Таблицы Room, RoomBooking, Lesson.roomId; публичное расписание аудитории; гонки броней. Ответить на 3 вопроса, P1/P2/P3. Ничего не править.

## Ответ Codex

На три вопроса:

1. **Раскладка в коде — нормально.** Геометрия SVG — в `plans.ts`, состояние занятости и правила бронирования — из БД. ID аудиторий должны быть стабильными. Коворкинг в этой модели бронируется **целиком**, вместимость не означает количество независимо бронируемых мест — указать это в интерфейсе.

2. **`FOR UPDATE` на Room достаточно против пересечения броней одной аудитории**, если все изменения проходят через эту блокировку и проверки выполняются внутри транзакции. Но квоты студента требуют дополнительной блокировки — ниже. `EXCLUDE` с `btree_gist` для прототипа необязателен; он всё равно не защитит от пересечения с отдельной таблицей Lesson.

3. **Шаблонные ссылки допустимы через строгий структурный валидатор.** Проверять пару «корпус + аудитория», реальную дату и горизонт, допустимый тип заявки и поля его каталога. Отклонять неизвестные/повторяющиеся параметры; значения кодировать через `URLSearchParams`. Никаких изменений при открытии ссылки — только видимое предзаполнение и отдельное подтверждение.

**P1 не вижу. Замечания до реализации:**

1. **P2 — блокировка Room не защищает квоты студента.** [rooms.md:33](/home/acid/projects/MGIMO/docs/plans/rooms.md:33): два параллельных запроса одного студента в разные аудитории независимо пройдут проверку «одна в день» или превысят две будущие брони. Блокировать также строку `StudentProfile`, всегда в одинаковом порядке, например студент → аудитория. Добавить конкурентные тесты разных комнат, включая случай одной уже существующей брони.

2. **P2 — бронирование и расписание должны использовать согласованное место занятия.** [rooms.md:23](/home/acid/projects/MGIMO/docs/plans/rooms.md:23): `roomId`, `buildingId` и строковый `room` могут разойтись. Нужен единый порядок обновления; онлайн-занятие не занимает аудиторию. При переносах также брать блокировку Room и проверять конфликт либо явно оставить расписание неизменяемым в демо. Пересечение считать как `existing.startsAt < end && existing.endsAt > start`: соседние интервалы допустимы.

3. **P2 — seed недостаточен для существующей БД.** [rooms.md:19](/home/acid/projects/MGIMO/docs/plans/rooms.md:19): нужны создание Room и заполнение `Lesson.roomId` без разрушительного общего seed. Иначе старые пары с `roomId = null` окажутся невидимыми проверке занятости. Проверять сопоставление не только описания схемы, но и существующих занятий.

4. **P2 — обновить границы публичного доступа в AGENTS.md.** [rooms.md:38](/home/acid/projects/MGIMO/docs/plans/rooms.md:38): сейчас исключение аудиторий не содержит. Возвращать отдельные DTO: чужая бронь — только интервал «занято», без ID, владельца и цели; чужая пара — разрешённые публичные поля без ID/истории. Проверять сериализованные данные, не только видимый HTML. «Мои брони» фильтруются по сессии; чтение/отмена чужого ID — 404.

5. **P2 — согласовать ссылки, санитайзер и состояние формы.** [rooms.md:61](/home/acid/projects/MGIMO/docs/plans/rooms.md:61): текущий [answer.ts:7](/home/acid/projects/MGIMO/src/lib/assistant/answer.ts:7) отвергает кириллицу и `+`, используемый для пробелов. Нужен общий валидатор канонических URL вместо расширения regex до произвольной строки. AGENTS.md также должен разрешать проверенные шаблоны. Для двух ссылок одного типа с разным предзаполнением обычного `defaultValue` недостаточно: форма должна корректно обновиться без старых значений.

6. **P2 — уточнить временные границы и квоты.** [rooms.md:30](/home/acid/projects/MGIMO/docs/plans/rooms.md:30): хранить `timestamptz`; сервер проверяет начало в будущем, шаг с нулевыми секундами, длительность, окончание до 21:00 того же московского дня. Определить календарное или скользящее окно семи дней. Дневная квота должна учитывать уже прошедшую подтверждённую бронь, иначе после её окончания можно бронировать повторно.

7. **P3 — SVG не гарантирует доступность после масштабирования.** [rooms.md:54](/home/acid/projects/MGIMO/docs/plans/rooms.md:54): проверить фактические цели ≥44 px, видимый фокус и открытие нужного этажа из deep link. На 360 px список должен давать полноценный путь бронирования. Для модальной панели нужны Escape и возврат фокуса. Запрета нативного `<select>` в AGENTS.md нет — не усложнять ради этого прототип.

## Что сделал Claude

Учтено в реализации:
1. Блокировки «студент → аудитория» в одной транзакции; тесты гонок (одна аудитория — два студента; один студент — две аудитории).
2. Пересечение `a.from < b.to && a.to > b.from`; онлайн-пары не получают `roomId`; расписание в демо меняется только seed-ом (зафиксировано в плане).
3. Неразрушающий `scripts/sync-rooms.ts` (`npm run db:rooms`): upsert аудиторий и пересчёт `Lesson.roomId`; тест «занятий без аудитории — 0».
4. AGENTS.md: исключение для аудиторий; DTO чужой брони — только интервал; тест по сериализованным данным.
5. Общий валидатор `src/lib/assistant/links.ts` (канонический вид через URLSearchParams), `prefillFor`, форма пересоздаётся по `key`.
6. Время: шаг 30 мин, 08:00–21:00 МСК, скользящее окно 7 дней, дневная квота считает и прошедшие брони.
7. Список бронируемых аудиторий под схемой; панель не модальная (без ловушки фокуса).
