# Codex 07 — ревью плана физкультуры (2026-11-10)

Сессия: 01a1bfe2-fee7-71d1-8d1a-66ab06413479 (resume, read-only)

## Промпт (от Claude Code, кратко)

> Ревью docs/plans/sport.md до реализации: модель, честность алгоритма, демо-кнопка жеребьёвки,
> синтетические участники, что упростить.

## Ответ Codex

1. **P1 — уникальности жеребьёвки и блокировки слота недостаточно.** [План, стр. 25–40](/mnt/c/MGIMO/docs/plans/sport.md:25): две одновременные записи одного студента в разные слоты могут обе пройти проверку квоты. Для MVP сериализовать **все изменения одной недели** через блокировку её строки: жеребьёвку, предпочтения, запись, отмену и продвижение очереди. Проверки и запись результата — внутри транзакции; повторный запрос не создаёт повторных действий.

2. **P1 — студенческая демо-кнопка закрывает неделю другим участникам.** Первый эксперт нажмёт её раньше, чем второй сохранит предпочтения. Для жюри кнопка приемлема как явно обозначенная демонстрация, но лучше изолированный сценарий на тестовый аккаунт. Более простой вариант — запуск только сотрудником по готовому сценарию. Серверный флаг демо, разрешённые аккаунты, фиксированная допустимая неделя; клиент не передаёт `seed` и участников. Сброс — только CLI.

3. **P1 — не определены закрытие приёма и снимок входных данных.** Добавить неделе состояния `OPEN / DRAWN`, дедлайн и сохранённый порядок участников. После закрытия предпочтения неизменяемы. Распределение и фиксация `DRAWN` атомарны: сбой не должен оставлять половину броней либо пустую «проведённую» жеребьёвку.

4. **P2 — очередь может нарушить принцип «сначала каждому одно место».** Сейчас она упорядочена только жеребьёвкой: студент с одной бронью может получить вторую раньше студента без мест. При освобождении выбирать сначала подходящих с **нулём записей**, затем с одной; внутри категории — порядок жеребьёвки. Перед выдачей повторно проверять квоту, расписание и переходы. Свободная запись не обходит очередь.

5. **P2 — нужны точные правила отмены и квоты.** Предлагаю демо-правило: до начала отмена возвращает место и квоту; после начала — `MISSED`, квота потрачена. `CONFIRMED`, `ATTENDED`, `MISSED` учитываются в лимите двух; `WAITLIST` — нет. При уникальной паре студент–слот повторная запись обновляет существующую отменённую бронь. Отмена самой тренировки требует отдельного статуса слота и уведомления участников.

6. **P2 — перенос пары после распределения пока не обработан.** Повторно проверять затронутые брони, отмечать конфликт и уведомлять студента; не отменять молча. Проверка доступности должна учитывать занятия **и другие спортивные брони**, оба перехода и переодевание. При приблизительном расчёте писать «по нашей оценке времени недостаточно», без категоричного обещания.

7. **P2 — модели не хватает семестра и источника начислений.** Нужны привязка прогресса и дополнительных баллов к семестру, даты посещения/начисления, запрет двойного начисления за бронь. Посещение и дополнительные баллы студент не назначает себе. Для первой версии достаточно вычислять тренировочные баллы как `ATTENDED × 5`, без отдельного журнала начислений.

8. **P2 — синтетические участники требуют решения на уровне FK.** Сейчас `StudentProfile.userId` обязателен. Проще создать синтетические `User` **без Account и Session**, сохранив связь профиля, чем делать её nullable. Дать им расписание и применять те же ограничения. В интерфейсе обозначить симуляцию конкуренции; чужие предпочтения, имена и расписания не раскрывать.

9. **P3 — объяснения должны отражать реальную причину.** «Первый выбор заполнен» неверно, если он исключён пересечением или переходом. Сохранять код причины. Позицию очереди вычислять по подходящим кандидатам, а не хранить неизменяемым числом. Прогресс показывать одновременно: **общие баллы / 100** и **тренировочные / 60**.

10. **На 1–2 дня:** отложить свободную запись, интерфейс начисления дополнительных баллов и улучшение уже выданных мест. Оставить предпочтения → два прохода → результат → отмена → автоматическое продвижение очереди, плюс включение подтверждённых тренировок в общее расписание. Обязательные проверки: повторный запуск, параллельные записи при одной оставшейся квоте, последнее место, отмена с очередью, конфликт после переноса и доступ A/B.
